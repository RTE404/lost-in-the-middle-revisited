# Rebalance the free rerun toward full questions

The plan can run as scoped, but four of its assumptions don't hold as of 30 September 2026, and its sample sizes are set in the wrong place. The authors' repo ships everything the plan needs: 2,655-question position files, the oracle file, the prompt templates and the scorers. Kaggle's T4 x2 is still the right free platform, and vLLM 0.18.x with Triton attention has been validated on it this August and September. Now the four problems. First, the GPU estimate of "1.5–2 hours per model" is optimistic: realistic figures are about 2.1 h for the 3B model and 2.9 h for a 4B model. Second, "Qwen3-4B with thinking off" should become **Qwen3-4B-Instruct-2507**. Third, "no extra system prompt" cannot be done literally with Qwen2.5, whose template injects a default one. Fourth, "recency-only is expected" is only one of three outcomes the recent literature supports. The biggest problem is statistical. At n=500 the main contrast can only detect gaps of about **5–6 points**, and recent 7–8B studies report gaps of **5–7 points**. The KV test at 100 examples can only detect gaps of about **7–10 points**. The power analysis in the notes wants all **2,655 questions** and **1,000+ KV items at 7 positions**. That costs about **38 GPU-hours** and goes over a 30-hour weekly quota under realistic assumptions. The fix: run **all 2,655 questions** (only about 3–4 extra GPU-hours per model, because 3K-token prompts are cheap), cut KV to the authors' **500 examples at 5 positions** with a **200-example stopping point**, and replace the full "rerun" check with a subset rerun. Total: about **21 GPU-hours**, or about **12.4 hours of wall-clock** on the two T4s. It fits in one quota week under the 1x-burn reading and needs the KV stopping rule under the 2x reading.

## The authors' repo covers the data, prompts and scoring, with five traps

**What the plan assumes (sections 2, 4 and 6).** Use the authors' data files with the answer already placed at each position. Copy their scoring function and prompt text. Choose 500 questions by seeded ID. Put the paper prompt in each model's chat template with no extra system prompt.

**What the repo actually contains.** It has everything needed for multi-document QA. `qa_data/` holds gzipped JSONL files: one oracle file plus 20-document files with the gold passage at **0-based indices 0/4/9/14/19**, which are the plan's positions 1/5/10/15/20. Every file checked holds **2,655 examples in the same question order** ([TREE](https://api.github.com/repos/nelson-liu/lost-in-the-middle/git/trees/main?recursive=1); [README](https://github.com/nelson-liu/lost-in-the-middle/blob/main/README.md)). Neither baseline has its own file. Oracle is the normal `qa.prompt` run on `nq-open-oracle.jsonl.gz`. Closed-book is the same file with `--closedbook`, which drops the documents and switches to `closedbook_qa.prompt` ([EXPERIMENTS.md](https://github.com/nelson-liu/lost-in-the-middle/blob/main/EXPERIMENTS.md)). The data was **re-uploaded on 2024-01-04**. The first release used mismatched query and passage embedders, which made the negatives easier ([issue #14](https://github.com/nelson-liu/lost-in-the-middle/issues/14)), so any older mirror is stale. The repo has had no pushes since then.

**Five traps the plan doesn't mention.**

1. **The examples have no ID field.** The keys are `question`, `answers`, `ctxs` and `nq_annotated_gold`. The plan's "saved list of IDs" therefore has to be line indices, and the pipeline should check that the question text matches across all five position files. Also, the gold passage has **no `id`, `score` or `original_retrieval_index`**, so code that expects those fields on every document will crash ([make_qa_data_from_retrieval_results.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/make_qa_data_from_retrieval_results.py)).
2. **QA and KV use different scorers.** QA uses `best_subspan_em`: SQuAD-normalize, then check whether any gold answer is a substring ([metrics.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/src/lost_in_the_middle/metrics.py)). But `evaluate_qa_responses.py` first **keeps only the first line**, with `model_answer.split("\n")[0].strip()`. Because the split happens before the strip, an output that starts with a newline scores 0 ([evaluate_qa_responses.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/evaluate_qa_responses.py)). The authors' Llama-2 vLLM script strips generations before scoring ([get_qa_responses_from_llama_2.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/get_qa_responses_from_llama_2.py)), and the plan should do the same. KV scoring is a plain case-insensitive substring match with no normalization and no first-line cut ([evaluate_kv_responses.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/evaluate_kv_responses.py)). The plan's rule "correct if any gold answer appears in the output" leaves out the first-line cut, and that changes scores.
3. **KV positions are not pre-built.** Each of the three KV files has **500 examples** with the gold record at a random position. The scripts move it at runtime with `pop`/`insert` to `--gold-index`. The authors list positions only for 140 keys (`0 34 69 104 139`, five evenly spaced), not for 300 ([get_kv_responses_from_mpt.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/get_kv_responses_from_mpt.py); [EXPERIMENTS.md](https://github.com/nelson-liu/lost-in-the-middle/blob/main/EXPERIMENTS.md)). The generator is unseeded ([make_kv_retrieval_data.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/make_kv_retrieval_data.py)), so "more than 500 KV items" means leaving the authors' data.
4. **`pip install -e .` fails.** It breaks on `triton-pre-mlir`/`flash-attn` ([issue #7](https://github.com/nelson-liu/lost-in-the-middle/issues/7)), and `requirements.txt` pins `vllm==v0.2.1.post1` ([requirements.txt](https://github.com/nelson-liu/lost-in-the-middle/blob/main/requirements.txt)). Vendor `prompting.py`, `metrics.py` and `prompts/` under the MIT license instead ([LICENSE](https://github.com/nelson-liu/lost-in-the-middle/blob/main/LICENSE)). Install `pydantic`, `regex` (imported but not listed) and `xopen`. Run `tests/test_prompting.py`, because `prompting.py` was written for pydantic v1 and nobody has checked it on v2.
5. **The authors did use system prompts.** Llama-2-chat was wrapped in Meta's default system prompt, and prompts over 4,096 tokens were **skipped, not truncated** ([get_qa_responses_from_llama_2.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/scripts/get_qa_responses_from_llama_2.py)). A model's default template is therefore closer to the authors' practice than a hand-stripped one.

**Other checks on the plan's numbers.** The paper labels 20 documents as **about 4K tokens**, not 3K, and 300 KV pairs as **about 16K**, not 15K ([Liu et al.](https://arxiv.org/pdf/2307.03172)). The authors report a 20-document maximum of 3,920 OpenAI tokens ([issue #6](https://github.com/nelson-liu/lost-in-the-middle/issues/6)), and Yu et al. measured about 2.3K with their tokenizer ([Yu et al. 2025](https://aclanthology.org/2025.findings-acl.316.pdf)). The plan's pre-run token count is the right safeguard. The notes confirm GPT-3.5's **56.1% closed-book / 88.3% oracle** ([Liu et al.](https://arxiv.org/pdf/2307.03172)). They did not re-check the Table 6 per-position values (75.8/57.2/53.8/55.4/63.2), so check those against the PDF before plotting. `EXPERIMENTS.md` also gives open-model reference curves that are easy to reproduce. Llama-2-70b-chat, for example, scores **.568/.533/.541/.597/.695** at positions 0/4/9/14/19 ([EXPERIMENTS.md](https://github.com/nelson-liu/lost-in-the-middle/blob/main/EXPERIMENTS.md)). That makes a better second reference line than a closed API model.

**Recommended changes.** Pin the repo commit SHA. Use line indices as IDs. Vendor the prompting and metric code. Apply the first-line rule after stripping leading whitespace. Use the KV scorer for KV. Move the gold KV record at runtime with the authors' code. Record the fully rendered prompt string, including any template-injected system prompt, and don't try to suppress it. Plan section 10's first add-on, "question before and after", is already implemented as `qa_with_query_aware_contextualization.prompt` and `kv_retrieval_with_query_aware_contextualization.prompt` ([prompting.py](https://github.com/nelson-liu/lost-in-the-middle/blob/main/src/lost_in_the_middle/prompting.py)).

## Kaggle T4 x2 is still the only practical free option, and P100 is now broken

**What the plan assumes (section 6).** T4 x2 rather than P100, "Save Version" background runs of up to 12 hours, one model per GPU, the HF token in Kaggle Secrets, and Colab only as a backup.

**What is true in late 2026.** All of this holds, plus two facts the plan doesn't have. Kaggle's free GPUs are still **P100 (16 GB) or T4 x2 (2×16 GB)** with 32 GB RAM ([AIMultiple, 2026-09-16](https://aimultiple.com/free-cloud-gpu)). The weekly quota floats at **about 30 hours** ([LuminoAI, 2026-03-27](https://www.luminoai.in/blog/kaggle-gave-you-12-hours-your-training-job-needed-more)), and sessions are capped at **about 12 hours** ([HF knowledge-base summary of Kaggle docs](https://huggingface.co/datasets/John6666/knowledge_base_md_for_rag_1/blob/main/kaggle_20251121.md)). The first new fact is that the P100 is now worse than "vLLM doesn't support it". Kaggle's current PyTorch (cu128) has **no sm_60 kernels at all**, and an issue opened 2026-03-20 is still open ([docker-python#1546](https://github.com/Kaggle/docker-python/issues/1546)). vLLM itself requires **compute capability 7.5+** ([vLLM install docs](https://docs.vllm.ai/en/latest/getting_started/installation/gpu.html)). The second is that interactive sessions die after **20 minutes idle**, so Save Version really is required, and `/kaggle/working` holds about 20 GB ([LuminoAI](https://www.luminoai.in/blog/kaggle-gave-you-12-hours-your-training-job-needed-more)). Raw outputs will be a few tens of MB, so size is not a concern.

**One unresolved conflict affects the budget.** Kaggle's own T4 x2 announcement says one hour on 2×T4 "only consumes 1 hour of your GPU quota" ([Kaggle product-feedback/361104](https://www.kaggle.com/product-feedback/361104)). A 2026 blog with no source says it burns **2 hours per clock hour** ([LuminoAI](https://www.luminoai.in/blog/kaggle-gave-you-12-hours-your-training-job-needed-more)). The primary source is older but authoritative. Settle the question empirically: read the quota meter before and after the pilot. One source lists a 9-hour Kaggle session limit ([Thunder Compute](https://www.thundercompute.com/blog/colab-alternatives-for-cheap-deep-learning-in-2025)), but that is probably the TPU cap. Kaggle Secrets is the standard way to store tokens, but the notes found no dated 2026 source for it.

**Colab is only a fallback for small jobs, as the plan says.** Sessions last at most 12 hours, the GPU type is not guaranteed, limits are unpublished, and **background execution is paid-only** ([Colab FAQ](https://research.google.com/colaboratory/faq.html)). Kaggle's image is now built on the Colab runtime image dated 2026-09-17 ([Dockerfile.tmpl](https://raw.githubusercontent.com/Kaggle/docker-python/main/Dockerfile.tmpl)), so the two software stacks are close. If Kaggle quota runs short, better top-ups are Lightning AI (15 monthly credits, about 22 T4-hours) and Modal ($30/month of credits) ([AIMultiple](https://aimultiple.com/free-cloud-gpu); [Thunder Compute](https://www.thundercompute.com/blog/colab-alternatives-for-cheap-deep-learning-in-2025)). SageMaker Studio Lab **closed to new customers on 30 July 2026** ([AWS](https://docs.aws.amazon.com/sagemaker/latest/dg/studio-lab-availability-change.html)).

## vLLM 0.18.1 runs on T4, but the time estimate is 1.4–1.5x too low

**What the plan assumes (sections 3, 6 and 9).** vLLM runs on a T4, perhaps after pinning an older version. Each model takes 1.5–2 GPU-hours, so the whole job takes about 2 hours with one model per GPU.

**vLLM support is confirmed, with specific settings.** Since V0 was removed, vLLM runs only the V1 engine. On sm75 it uses the **TRITON_ATTN** backend, because FlashAttention needs sm80 or newer. The best-validated setup on Kaggle 2×T4 (August–September 2026) is **vLLM 0.18.1 with PyTorch 2.10.0+cu128**, `dtype="float16"`, `enforce_eager=True` and `disable_custom_all_reduce=True`, and it was validated with Qwen2.5-3B ([kaggle-vllm](https://github.com/kaggle-vllm/kaggle-vllm)). A second project ran vLLM 0.18.0 on a Kaggle T4 at the end of September ([vllm-t4-lab](https://github.com/Placidoe/vllm-t4-lab)). Releases from **v0.22.0** on crash on T4 when FlashInfer is auto-selected ([PR #44403](https://github.com/vllm-project/vllm/pull/44403)). A fix merged on 2026-06-23 moves sm75 back to TRITON_ATTN ([PR #45375](https://github.com/vllm-project/vllm/pull/45375)), but the notes could not tell which release first includes it. A plain `pip install vllm` can clash with Kaggle's preinstalled stack, and kaggle-vllm installs with `--target --no-deps` for that reason ([kaggle-vllm](https://github.com/kaggle-vllm/kaggle-vllm)). The same project found that **TP=1 beats TP=2** for small models, which supports the plan's choice of one model per GPU.

**The time estimate.** No published source measures vLLM prefill on a T4 for 3–4B models. The workload is almost all compute-bound prefill, so the estimate comes from FLOP counts. At a realistic 20 TFLOPS effective, a 3B model processes about **3,300 tok/s at 3K context and 2,600 tok/s at 15K**. A 4B model processes about **2,500 and 1,700 tok/s**. This matches a llama.cpp 7B anchor of about 16 TFLOPS effective on a T4 ([llama.cpp #15013](https://github.com/ggml-org/llama.cpp/discussions/15013)). On those rates the plan as written costs **about 2.1 h for Qwen2.5-3B and about 2.9 h for a Qwen3-4B-class model**. The range runs from 1.6 h to 4.7 h depending on efficiency. With one model per GPU, the wall-clock time is the slower model's, **about 3 hours, not 2**. The 15K KV prompts are **more than half the plan's compute** even though they are only 700 of 4,200 prompts.

**Memory is fine.** At 15K tokens, fp16 KV cache fits about 10 concurrent sequences for Qwen2.5-3B (36 KiB/token) and about 1 for Qwen3-4B (144 KiB/token). Long prefill is compute-bound, so low concurrency barely costs throughput ([Qwen2.5-3B config](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/raw/main/config.json); [Qwen3-4B card](https://huggingface.co/Qwen/Qwen3-4B)). Set `max_model_len` explicitly to about 16–18K. Without it, a 262K-native model will fail vLLM's startup memory check.

**Recommended changes.** Pin `vllm==0.18.1` and let it install its own torch before torch is imported, then restart the kernel. Set `VLLM_ATTENTION_BACKEND=TRITON_ATTN` in every version. Set `dtype=float16`, `gpu_memory_utilization` of about 0.85–0.9, and `max_model_len` of about 18K. Budget from a **100-prompt pilot's measured tok/s**, not from the plan's guess. For the fallback, use HF transformers with **SDPA attention**: eager attention at 15K tokens needs about 7 GB per layer and runs out of memory. Also sort prompts by length before batching.

## Replace hybrid Qwen3-4B with Qwen3-4B-Instruct-2507

**What the plan assumes (section 3).** Qwen2.5-3B-Instruct is the 2024 reference, and Qwen3-4B with thinking off (or the newest small model) is the current model. Both fit in fp16.

**Qwen2.5-3B-Instruct is a sound reference, with two caveats.** It has a 32K context and ships in bf16. Unlike its siblings, it is under the **Qwen Research license**, not Apache 2.0 ([model card](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct)). Its chat template **inserts "You are Qwen, created by Alibaba Cloud. You are a helpful assistant."** whenever no system message is given ([tokenizer_config.json](https://huggingface.co/Qwen/Qwen2.5-3B-Instruct/raw/main/tokenizer_config.json)), so the plan's "no extra system prompt" rule can't be met as written. Other small Qwen2.5 models have produced inf/NaN in fp16 ([QwenLM/Qwen#848](https://github.com/QwenLM/Qwen/issues/848)), and the usual fix, FlashAttention-2, is unavailable on T4. The plan's rule 6 ("suspect fp16 if oracle looks broken") is right, but it should be a **pre-run smoke test on a 16K prompt**.

**Hybrid Qwen3-4B adds friction the plan doesn't need.** With `enable_thinking=False`, the template **appends an empty `<think>\n\n</think>\n\n` to the prompt** ([Qwen3-4B tokenizer_config](https://huggingface.co/Qwen/Qwen3-4B/raw/main/tokenizer_config.json)). **Qwen3-4B-Instruct-2507** is non-thinking only, never emits think tags, has a 262K native context, and is Apache 2.0. Its architecture matches Qwen3-4B (36 layers, 32 Q / 8 KV heads), so the cost and memory estimates are unchanged ([2507 card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)). Choosing it removes the plan's "thinking text breaks scoring" risk.

**The newest small models are riskier on a T4.** **Qwen3.5-4B** (2 March 2026) is the newest ≤4B Qwen. Later Qwen generations released no small sizes ([Wikipedia: Qwen](https://en.wikipedia.org/wiki/Qwen)). Qwen3.5-4B is a hybrid of Gated DeltaNet and attention, thinks by default, is multimodal, and **requires vLLM nightly/main** ([Qwen3.5-4B card](https://huggingface.co/Qwen/Qwen3.5-4B)). Its linear-attention Triton kernels have failed on older and non-NVIDIA GPUs ([vLLM #45929](https://github.com/vllm-project/vllm/issues/45929)). **Gemma 4 E2B** (April 2026) uses 512-token sliding windows in 28 of 35 layers ([config](https://huggingface.co/google/gemma-4-E2B-it/raw/main/config.json)). That confounds a position study, and the Gemma family has a history of fp16 overflow ([Unsloth](https://unsloth.ai/docs/models/tutorials/gemma-3-how-to-run-and-fine-tune)). Gemma 4 E4B (8B total parameters) doesn't fit on a T4 in fp16. No source reports either model running on a T4. Qwen3.5-4B belongs in the "add later" list, behind a smoke test. Keep greedy decoding despite Qwen's recommended T=0.7, because comparability with the paper comes first. For section 10's Llama-3.2-3B add-on, note that its 112 KiB/token KV cache allows about 3 concurrent 15K sequences.

## Recency-only is one of three live outcomes, and the closed-book floor will be low

**What the plan assumes (sections 2 and 5).** Small models may show recency only, as Llama-2-7B did. 20 documents is short for modern models, and KV at about 15K is the long-input check.

**The size precedent is real but old.** Liu et al. found Llama-2-7B "solely recency-biased", with the U-shape appearing only at 13B and 70B ([Liu et al.](https://arxiv.org/pdf/2307.03172)). Newer evidence points other ways. Veseli et al. found Llama-3.1-8B tracking its 70B siblings and argue size "isn't the primary driver". In their data the effect is strongest when the input fills about **25–38% of the context window**, and it "vanishes or diminishes significantly" beyond 50%, where the ranking flips to last>middle>first ([Veseli et al. 2025](https://arxiv.org/html/2508.07479)). July 2026 text ablations on 7–8B Qwen and InternVL readers, using the NQ-Open protocol, show **primacy dominance** with first-vs-last gaps of **+5.2 to +7.4 points** ([Lost at the End](https://arxiv.org/html/2606.16494v3)). Older 7B chat models showed much larger dips: Vicuna-7B-16k scored 71.9% → 47.3% → 50.7% at positions 1/10/20 ([Hsieh et al. 2024](https://arxiv.org/html/2406.16008)).

**Relative length points to specific predictions.** No source measures 1–4B models at under 10% of their window, so these are inferences. The 20-document test fills about 9% of Qwen2.5-3B's 32K window and about 1% of 2507's 262K window. That is well below Veseli's peak, so expect a **weak** effect, not a missing one. The KV test at 15K fills **about 47% of Qwen2.5-3B's window**, the zone where primacy collapses, so recency-leaning is the natural prediction there. It fills only about 6% of 2507's window. Exact-match KV may also hit the ceiling: a 2026 KV-only reproduction found **99.2%** for Llama 3.3 70B at 300 keys with a 0.5-point edge-minus-middle gap, and 96.2% for Gemini 2.0 Flash-Lite with a 3.8-point gap ([berberberk](https://github.com/berberberk/lost-in-the-middle)). Latent-association retrieval degrades far more than literal matching ([NoLiMa](https://arxiv.org/abs/2502.05167)).

**The "worse than no documents" comparison is unlikely to repeat.** GPT-3.5's closed-book score was 56.1%. Small models know much less NQ: one unverified figure puts Qwen2.5-3B at **about 13.6%** ([Pandey 2026](https://arxiv.org/abs/2603.11513)). The same paper warns of a bigger risk: models of 7B or smaller "fail to extract the correct answer 85 to 100 percent of the time" on some splits even with oracle retrieval. The plan's step 2 gate ("oracle well above closed-book") is therefore essential, not a formality. Pre-register all three shapes. Treat the closed-book-wrong subset as a secondary analysis, and report relative input length next to token counts.

## Statistics: 500 questions only catch gaps larger than modern models show

**What the plan assumes (sections 4, 5 and 8).** A paired bootstrap on 500 questions, verdicts based on whether 95% CIs exclude 0, "first and last beat the worst middle position", and reruns within ±2 points.

**The design is paired correctly, but underpowered.** Paired tests over questions are standard: McNemar or a paired bootstrap ([Dror et al. 2018](https://aclanthology.org/P18-1128/); [Miller 2024](https://arxiv.org/abs/2411.00640)). The 2026 position-bias paper above used the plan's exact paired bootstrap with 10,000 resamples ([Lost at the End](https://arxiv.org/html/2606.16494v3)). The weak point is power. The minimum detectable effect is MDE ≈ (z₁₋α/₂ + 0.84)·√(d/n), where d is the share of questions that flip between two positions ([Card et al. 2020](https://arxiv.org/abs/2010.06595)). With Holm/Bonferroni over two pre-registered contrasts per model (α=0.025, multiplier 3.08), my computed MDEs are:

| Test | n | d=0.05 | d=0.10 | d=0.15 | d=0.20 |
|---|---|---|---|---|---|
| NQ 20-doc | 500 (plan) | 3.1 pt | 4.4 pt | 5.3 pt | 6.2 pt |
| NQ 20-doc | 2,655 (full) | 1.3 pt | 1.9 pt | 2.3 pt | 2.7 pt |
| KV 300-key | 100 (plan) | 6.9 pt | 9.7 pt | — | — |
| KV 300-key | 200 | 4.9 pt | 6.9 pt | — | — |
| KV 300-key | 500 (authors' full file) | 3.1 pt | 4.4 pt | — | — |

With discordance of 10–25%, which the notes assume and which a pilot must confirm, n=500 detects only gaps of about 5–6 points. The only modern small-model gaps reported (+5–7) sit right at that boundary. A "Flat" verdict at n=500 would mostly mean "underpowered". The analysis notes reach the same conclusion from uncorrected tables: n=500 has only **0.32–0.56 power for a 3-point effect** ([literature notes, Card et al. method](https://github.com/dallascard/NLP-power-analysis)).

**Two design fixes.** First, "the worst middle position" picks the minimum of three means after seeing the data, which biases the contrast in favour of finding a U. Pre-register **position 10 (index 9)**, or the mean of positions 5/10/15, as "middle". Alternatively use a single U-contrast, mean(first, last) − middle. For KV, use index 149 as the middle. Second, add an **"Inconclusive"** verdict: call a curve "Flat" only when the paired CI lies inside ±MDE. Report McNemar exact p-values next to the bootstrap CIs, and cluster by question if you pool models ([Miller 2024](https://arxiv.org/abs/2411.00640)).

## Resolving the budget conflict: full NQ set, staged KV, partial rerun

The notes conflict. The statistics notes want **all 2,655 questions** and **at least 1,000 KV items per position**. The GPU notes put the plan's much smaller design at 2–3 GPU-hours per model already. The arithmetic below uses the realistic rates from the vLLM notes, with 3K tokens per 20-doc prompt, about 250 per oracle prompt and 15K per KV prompt. Decode and overhead add 0.3–0.8 h per model.

| Design | Prompt tokens per model | Qwen2.5-3B | Qwen3-4B-2507 | GPU-h total | Wall-clock on T4 x2 |
|---|---|---|---|---|---|
| Plan as written (500 NQ×5 + 1,000 baselines; KV 100×7) | 7.6M + 10.5M | ≈2.1 h | ≈2.9 h | ≈5.0 | ≈2.9 h |
| Power-analysis maximum (2,655×5 + baselines; KV 1,000×7) | 40.5M + 105M | 3.4+11.2+0.6 ≈ 15.2 h | 4.5+17.2+0.8 ≈ 22.5 h | ≈37.7 | ≈22.5 h |
| **Recommended** (2,655×5 + 2,655×2 baselines; KV 500×5; subset rerun) | 40.5M + 37.5M + 8.3M | 3.9+4.0+0.8 ≈ 8.7 h | 5.2+6.1+1.1 ≈ 12.4 h | ≈21.1 | ≈12.4 h |
| Recommended with KV stopped at 200 | 40.5M + 15M + 8.3M | 3.9+1.6+0.8 ≈ 6.3 h | 5.2+2.5+1.1 ≈ 8.8 h | ≈15.1 | ≈8.8 h |

The maximum design fails on three counts. It needs **1,000 KV items that don't exist**: the authors' file has 500, and its generator is unseeded. It exceeds the 12-hour session cap for the 4B model even when split into NQ and KV runs. It consumes 22.5 quota hours at 1x burn and **45 at 2x**, against about 30 per week, before any debugging or rerun. The imbalance is the point: KV at 15K costs **about 5x more per prompt** than 20-doc QA, but KV is the test most likely to sit at the ceiling. When scores are at the ceiling, discordance is low, and at d=0.05 the authors' 500 items already give a 3.1-point MDE.

The recommended split spends compute where it buys power. Running all 2,655 questions costs only about **2.8 h (3B) and 3.7 h (4B) more** than 500 (7.5M → 39.8M tokens), and it cuts the NQ MDE from about 6 to about 2.7 points. For KV, use the authors' 500 examples at **five evenly spaced indices (0, 74, 149, 224, 299)**, mirroring their 140-key choice. Run it in stages. The first 200 examples at all five positions give an observed d. If d ≤ 0.05 (ceiling), stop at 200. Otherwise extend to 500 and report the achieved MDE. Plan step 6 re-runs everything, which would silently double the GPU bill. Instead, rerun **300 questions × 5 positions plus 50 KV × 5** in a fresh session, about 1.9 GPU-h in total. Require per-position accuracy within ±2 points and per-item agreement of at least 97%, and keep the plan's exact rescoring check.

Run it as three Save Version jobs per GPU: NQ (≤5.2 h), KV (≤6.1 h) and rerun (≤1.1 h), each well under the 12-hour cap and resumable from the `.jsonl`. At 1x burn this uses about 12.4 of 30 weekly quota hours. At 2x burn it uses about 24.8. If the pilot shows pessimistic efficiency (about 1.5x slower), the full KV run no longer fits in one week at 2x burn. In that case use the 200-item stopping point (≈8.8 h × 1.5 × 2 ≈ 26 quota hours), or spread the work across two quota weeks.

## Conclusion

The paper's released artifacts have held up for almost three years, so fidelity to the paper is not what threatens the reproduction. The threats are sample-size allocation and a few template and scoring details. Modern small models are expected to show small position gaps, around 5 points rather than the 20+ of 2023. The original plan spent its compute on the expensive 15K-token test, which likely sits at ceiling, and left the cheap, informative 3K-token test underpowered. Reversing that trade costs about 4x the GPU time and still fits the free tier. It also turns a likely "flat, but inconclusive" result into a defensible measurement at about 2.7-point resolution.

Two design choices are worth writing into the notebook's first cell alongside the verdict guesses: a fixed middle position, and an "Inconclusive" verdict tied to a stated MDE. Without them a null result can't be told apart from an underpowered one. The relative-length framing adds a new prediction: the same question may give a recency-leaning curve for Qwen2.5-3B on KV (about 47% of its window) and a weak U for 2507 (about 6%). A difference between those two would be a more interesting 2026 finding than a yes/no on "still lost in the middle".
